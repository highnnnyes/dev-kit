---
description: PROGRESS.md를 파싱해 계획 단위 실측 지표(재시도율·소요·병렬 효율)를 계산하고 README용 markdown 스니펫으로 출력한다
---

`$ARGUMENTS`로 지정된 PLAN.md 경로(생략 시 현재 프로젝트, 2개 지정 시
비교 모드)의 실행 기록에서 지표를 계산해 markdown 스니펫으로 출력하라.

**오케스트레이터가 직접 절차로 수행한다 — 서브에이전트 디스패치 금지**
(판단이 필요 없는 기계적 파싱·계산이라 위임은 토큰 낭비다).

원칙: **지표는 PROGRESS.md에 이미 남는 데이터에서만 계산한다.** 계측을
위해 루프에 새 기록 의무를 추가하지 않는다 (유일한 예외: v1.11의
`- 시작:` 1줄 — execute-plan 기록 계약 참조 / v1.15.2의 PLAN 완료 블록 — PLAN당
1블록, 사용자 지시로 v1.15 효과 판정 지표 ④를 위해 추가). v1.15의 `- 대상:` 줄은 계측용이
아니라 execute-plan 중단 조건 (j)의 계수 키로 도입된 것이고, 이 명령은 그
부산물을 읽기만 한다.

## 입력 (전부 기존 기록)

- `PROGRESS.md` + `PROGRESS.archive.md` (롤링 요약으로 압축된 과거분).
  archive 탐색: PROGRESS.md와 **같은 디렉토리**의 `PROGRESS.archive.md` —
  없으면 그 사실을 출력 첫 행(입력 파일)에 남긴다.
- mode B 계획이면 트랙 로컬 `PROGRESS.<트랙>.md` 파일들 포함
  (머지로 메인 히스토리에 보존됨)
- 파싱 대상 라인:
  - 블록 헤더 `## [날짜시각] Task N.M — [결과] · 시도 X회 · … · tier=… · risk=…`
    — 헤더 시각이 태스크 **종료(기록) 시점**이다
  - `- 시작: [날짜시각]` — 태스크 **착수 시점** (v1.11부터 기록)
  - `- FAIL사유: … 유형(…)` — FAIL 유형 분해용
  - `- red: CONFIRMED …` — red 확인 비율용
  - `- 대상: …` (v1.15부터) — 재정의 반복용
  - `## … PLAN 완료 — …` 블록의 `- 상류개입:`·`- 정정:` (v1.15.2부터) — PLAN별
    상류 개입·하류 정정용

## 산출 항목

- **태스크 수 / 완료·중단 수** — 헤더의 `[PASS|FAIL후PASS|BLOCKED]` 집계.
- **재시도율** = FAIL 총수 ÷ 태스크 수 (이 명령의 정의 — 헤더 `시도 X회`의
  X-1 합산이 FAIL 총수다). FAIL 유형별 분해:
  verify-gate / 리뷰 FAIL(컨벤션·기능 결함·verify 미충족·보안·기타) /
  red 미확인(verify-gate 중 FAIL사유에 red 재작성이 명시된 건) /
  유형 미기재(`- FAIL사유:` 라인 또는 유형 태그가 없는 FAIL — 롤링 요약
  압축분 등. 추정으로 분류하지 않는다).
  건강 범위 **10~30%** 대비 판정 코멘트 1줄 포함
  (0% 수렴 = 리뷰 형식화 의심, 30% 초과 = tier 배분·태스크 정의 재검토).
- **소요 시간** — 태스크별 [시작, 헤더 시각] 차분. 계획 총 월클럭은
  **[P]·트랙 병렬 구간의 겹치는 시간을 중복 합산하지 않는다** — 태스크
  시작·종료 구간의 **합집합**으로 계산한다. 태스크당 소요는 중앙값 셋으로
  분리해 보고한다 (전부 `- 시작:` 있는 건 한정, 각각 n 표기):
  ① **시도 1회 태스크 한정** — 재시도 루프가 섞이지 않은 순수 1회전 소요,
  ② **tier=light 한정**,
  ③ **300분 초과 이상치 제외** — 승인 대기·중단 방치가 섞인 구간 제거.
  판정 코멘트에 해석 규칙 1줄을 포함한다: ①이 높으면 루프 오버헤드가,
  낮으면 태스크 크기가 소요의 주 원인이다.
- **병렬 효율** (mode A/B 계획만) = 태스크 소요 합계 ÷ 월클럭 합집합
  = 실효 동시성. 이론 상한(mode A: 슬롯 3, mode B: 트랙 수) 대비 %.
- **red: CONFIRMED 비율** — tier=standard 코드 태스크 수 대비
  (`- red: CONFIRMED` 라인 수 ÷ tier=standard이면서 role≠docs인 태스크 수).
  **`- red:` 줄 부재 건수를 같은 행에 별도 표기한다** — red 미확인(FAIL)과
  기록 자체 누락은 다른 현상이다.

- **재정의 반복** (v1.15) — `- 대상:` 키별 사건 수 상위 5개. 사건 정의는
  execute-plan "대상 반복 정지"와 동일 — FAIL후PASS·`[verify 미통과]`
  BLOCKED 블록 중 FAIL사유 유형이 기능 결함·verify 미충족·verify-gate인 것
  (컨벤션 위반·보안·기타만이면 제외, `[전제 붕괴]` 제외) + 보완=stage-review·
  merge-fail·user-fix 블록. `계수 리셋` 줄 이후만 센다.
  형식: `R3 2 · screens#결과화면 1` — 3에 이른 키는 (j) 발동 여부를 병기.
  `- 대상:` 줄이 하나도 없으면 `n/a (v1.15 이전 기록)`.
- **기록 계약 준수** (v1.15) — 계약 위반 건수만 센다 (판정 아님):
  ① `- FAIL사유:` 줄 중 `유형(…)` 또는 유형 키워드(컨벤션 위반·기능 결함·
  verify 미충족·보안·verify-gate·기타)가 없는 줄 수, ② `- 시작:` 줄 중 값이
  날짜시각 형식이 아닌 줄 수(자리표시 문구 등). 근거: 진단 S16b — 유형 태그
  0/76, `- 시작:` 자리표시 21줄로 지표가 n/a가 됐다.

- **트랙별 대기 시간 (mode A/B, v1.16)** — [P] 그룹(mode A)·트랙(mode B)마다
  각 태스크·트랙의 **마지막 종료 시각 → 그룹 머지(mode B는 전 트랙 COMPLETE 후
  머지)** 간격을 대기 시간으로 보고, 그룹마다 `최대 대기 ÷ 그룹 월클럭`을
  불균형으로 낸다. 기존 기록(`- 시작:`·헤더 시각·`Group … 머지 후 통합검증`
  헤더 시각)만 쓴다. 머지 시각이 기록에 없으면 `n/a (머지 기록 없음)`.
  목적: 공유 큐 동적 배분 검토의 선행 실측 (dev-kit 리포 docs/v1.16-design.md §3).
- **상류 개입 / 하류 정정 (PLAN별, v1.15.2)** — PLAN 완료 블록마다
  `상류개입 N · 정정 M`을 나열한다. 정정 줄이 아직 없는 블록(다음 PLAN 미작성)은
  `정정 미기록`, PLAN 완료 블록이 하나도 없으면 `n/a (v1.15.2 이전 기록)`.
  상류 개입은 보고만 하고(증가가 의도된 지표), 판정 코멘트는 하류 정정에만 단다.

fix 커밋 비율·파일 핫스팟은 산출하지 않는다 — 진단(dev-kit 리포 docs/diagnosis-2026-10.md
§5)에서 판별력이 낮다고 확인됐다 (fix 비율 2.6~14.9%, 핫스팟은 기능 누적과
구분 불가).

## 출력 형식

표 1개 + 판정 코멘트 **3줄 이내**. README에 그대로 붙일 수 있는 markdown.

**출력 첫 행은 "입력 파일"로 고정한다 [엄격]** — 실제로 열어 파싱한 파일
경로와 각 파일의 태스크 블록 수를 적고, 열지 못한(없는) 파일은 `없음`으로
찍는다. 아래 예시 문구를 그대로 옮기는 것 금지 — 이 행은 실측 결과만
담는다. 읽지 않은 파일을 읽었다고 출력하는 것이 이 행이 막는 결함이다.

```markdown
| 지표 | 값 |
|---|---|
| 입력 파일 | `PROGRESS.md` 45블록 · `PROGRESS.archive.md` 없음 |
| 태스크 (완료/중단) | 12 (11/1) |
| 재시도율 (FAIL÷태스크) | 16.7% — verify-gate 1 · 리뷰 FAIL 1 · red 미확인 0 |
| 소요 중앙값 — 시도 1회 한정 | 5.5m (n=9) |
| 소요 중앙값 — tier=light 한정 | 3.0m (n=3) |
| 소요 중앙값 — 300m 초과 제외 | 6.0m (n=11, 제외 1건) |
| 총 월클럭 (병렬 합집합) | 58m |
| 병렬 효율 (mode A) | 1.8× (상한 3 대비 60%) |
| red: CONFIRMED | 8/9 (89%) — `- red:` 줄 부재 0건 |
| 재정의 반복 (상위) | R3 2 · screens#결과화면 1 — (j) 발동 0 |
| 기록 계약 준수 | 유형 누락 0줄 · `- 시작:` 비시각 0줄 |
| 트랙별 대기 시간 (mode A) | P2: 최대 대기 9m · 불균형 36% / P3: n/a (머지 기록 없음) |
| 상류 개입 / 하류 정정 (PLAN별) | 계약 정비: 상류 12 · 정정 3 / 2차 피드백: 상류 7 · 정정 미기록 |

> 판정: 재시도율 건강 범위(10~30%) 내. 시도 1회 중앙값이 높으면 루프
> 오버헤드가, 낮으면 태스크 크기가 소요의 주 원인. …
```

**비교 모드**: 인자로 계획 2개를 받으면 (`/dev-kit:metrics <계획A> <계획B>`)
동일 표를 열 2개로 나란히 놓고 마지막 행에 **단축률**(월클럭 기준)을
계산한다 — 순차(mode S) vs mode A 비교 용도. 두 계획의 규모(태스크 수)가
크게 다르면 코멘트에 명시한다.

## n/a 규칙 [엄격]

파싱 실패(타임스탬프 누락, `- 시작:` 없는 구버전 기록, archive 유실 등)는
**추정으로 메우지 말고** 해당 항목을 `n/a (사유)`로 표기한다 — 지표의
신뢰성이 이 명령의 존재 이유다. 일부 태스크만 누락이면 분모·분자에서
제외하고 제외 건수를 표기한다 (`소요 평균 6.2m — 시작 시각 누락 3건 제외`).
