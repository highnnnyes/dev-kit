기존 프로젝트를 현행 dev-kit 규격으로 마이그레이션하라. 원칙: **판정과
기입은 자동, 위험 판단은 보고** — 사람의 일은 보고를 읽고 결정하는 것까지만
남긴다. 아래 1~5를 순서대로 수행한다.

## 1. mode 판정·기입

PLAN.md 헤더에 `mode:` 라인이 없으면 write-plan의 실행 모드 판정 기준
(태스크 수 8/15, role 종수, 파일 겹침 — 애매하면 보수적으로 낮은 모드)으로
판정해 기록한다: `mode: A (오버라이드: migrate, 근거: …)`.

**B는 어떤 경우에도 자동 기입 금지 [엄격]** — B 조건에 해당해도 헤더에는
A를 기입하고, 최종 보고에 "B 후보 (트랙 분할 가능)"를 남긴다. B 진입은
write-plan의 승인 절차("B로 올려" → 분할안 출력 → 승인 기록)로만 가능하다.

이미 `mode:` 라인이 있으면 이 단계는 건너뛴다 (재판정은 migrate의 일이
아니다 — write-plan의 mode 재판정 트리거 참조).

## 2. 프로비저닝

1의 판정 결과(또는 기존 헤더의 mode)에 따라 write-plan의 프로비저닝 규칙과
동일하게 기입한다:
- mode A: 프로젝트 CLAUDE.md에 `worktree:` 선언이 없으면 canonical 형식으로
  추가(값은 스택으로 판정, 판정 불가면 기입하지 않고 보고), 테스트 리소스
  규칙("테스트는 테스트 전용 DB/리소스만 사용한다 — 개발·공유 DB 금지")이
  없으면 추가.
- mode S: 추가하지 않는다. 이미 있으면 제거하지도 않는다.

## 3. verify 정리

PLAN.md의 **미완료 태스크**의 verify를 전수 점검한다:
- allowlist 형태(패키지/빌드 스크립트 — `npm run *`·`pnpm *`·`yarn *`·
  `make *`·`pytest`·`go test`·`cargo test`·`tsc --noEmit`·프로젝트
  CLAUDE.md allowlist)가 아니거나, 파이프·`&&`·`;`·리다이렉션이 포함되면
  **동등한 패키지 스크립트로 교체**한다 — 필요 시 package.json의 scripts에
  해당 스크립트를 추가한다.
- **검증 강도 변경 금지 [엄격]**: 교체는 형태 변환일 뿐, 원래 verify가
  검사하던 범위·조건을 넓히거나 좁히지 않는다. 동등 변환이 불가능하면
  교체하지 말고 4의 보고 대상으로 넘긴다.
- 절차형 verify 2종(role=docs의 "drift 스캔 통과", harden의 "증거 칸
  충족")은 그대로 유지한다 — 명령 제약의 대상이 아니다.

## 4. 위험 항목 보고 [엄격]

다음은 **수정하지 않고** 목록으로 보고한다:
- 부수효과 있는 verify: DB 변경·파일 삭제·네트워크 쓰기
- 개발·공유 DB를 물고 있는 테스트 설정

해당 태스크 줄 끝에 `· hold: migrate(위험 보고 — 사용자 결정 대기)` 표시를
붙인다 — execute-plan은 이 표시가 있는 태스크를 건너뛰고 보고에 포함한다.
사용자가 결정하면 표시를 제거하고 재개 대상에 복귀한다.

## 5. 자기 검사·커밋

- 커밋 전에 수정 파일 목록을 검사한다: **PLAN.md·프로젝트 CLAUDE.md·
  package.json(scripts만) 3개를 벗어나면 커밋 없이 중단·보고한다 [엄격]**
  (package.json은 scripts 외 필드 변경도 위반이다).
- 정상이면 `[dev-kit-migrate] v<dev-kit 버전> 규격 반영` **단일 커밋**을
  만들고, 변경 요약·판정 근거·보고 항목(hold 목록)을 출력한다.
- 변경이 0건이면 커밋하지 않고 "변경 0건 — 이미 현행 규격"으로 보고한다.

## 멱등성 [엄격]

이미 마이그레이션된 프로젝트에 재실행해도 **변경 0건으로 통과해야 한다** —
재실행이 안전해야 기기·시점 혼재에서 쓸 수 있다. 각 단계는 "없으면 추가,
있으면 그대로" 원칙을 지키고, 이미 있는 선언·규칙·헤더를 재작성하거나
포맷을 정리하지 않는다 (Surgical Changes).
