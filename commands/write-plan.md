---
description: 설계/기능 요청을 PLAN.md로 분해한다 — 단계(stage) → verify 하나 단위 태스크(task, 테스트 1~2개 + 그 구현 · 대략 5~10분)
---

사용자가 준 설계(또는 $ARGUMENTS로 지정된 문서/기능 설명)를 분석해서
프로젝트 루트에 PLAN.md를 작성하라. 이미 PLAN.md가 있으면 덮어쓰지 말고
기존 진행 상황을 보존하면서 병합하라.

## 분해 원칙
1. 먼저 관련 코드를 실제로 읽어라. 코드를 안 본 계획은 금지 (파일 경로·기존 패턴 확인).
2. **단계(stage)**: 독립적으로 검증 가능한 기능 단위. 각 단계는 완료 조건을 가진다.
3. **태스크(task)**: 한 단계를 **verify 하나로 통과/실패가 갈리는 단위 —
   신규/확장 테스트 1~2개 + 그 구현**으로 쪼갠 것 (대략 5~10분).
   이 범위를 넘으면 더 쪼갠다.
   근거: 에이전트는 소요 시간을 추정하지 못하지만 "verify 하나"는 산출물로
   확인 가능하다 — 강제되는 기준은 관측 가능한 기준이다. 시간은 감을 잡기
   위한 참고치일 뿐 판정 기준이 아니다.
   각 태스크는 반드시:
   - 정확한 파일 경로 (신규 생성이면 "신규" 표기)
   - 한 문장 목표
   - verify 방법 (실행할 테스트/명령, 확인할 출력).
     **[엄격] tier=standard 코드 태스크의 verify는 그 태스크가 추가한 동작을
     검증하는 신규/확장 테스트를 명시해야 한다.** "기존 테스트 통과"만으로는
     verify 미달 — 태스크를 다시 정의하라. 프로젝트에 테스트 인프라가 없으면
     Stage 1에 테스트 셋업 태스크를 넣어라.
     **[엄격] verify는 부수효과 없는 명령만 허용한다.** 실행 루프의
     오케스트레이터가 이 명령을 직접 실행하므로(verify 선행 게이트·red 확인 —
     execute-plan 참조) 자동 실행 가능한 형태로 쓴다: 패키지/빌드 스크립트
     (`npm run *`·`pnpm *`·`yarn *`·`make *`·`pytest`·`go test`·`cargo test`·
     `tsc --noEmit` 또는 프로젝트 CLAUDE.md allowlist 명령). `rm`·`drop`·
     `truncate`·`delete`·`reset`·`migrate`·`push`·`deploy`·`curl`/`wget`,
     파이프·`&&`·`;` 연쇄, 리다이렉션이 들어간 verify는 작성 금지.
     DB를 건드리는 테스트는 테스트 전용 리소스(테스트 DB·컨테이너·인메모리)
     대상임이 verify 문구 또는 프로젝트 CLAUDE.md에서 확인 가능해야 한다 —
     확인 불가하면 태스크로 만들지 말고 DECISIONS로 올려 계획 실행 전에
     멈춰라. 개발 DB·공유 리소스를 대상으로 하는 verify는 작성 자체를 금지한다.
     (명령이 아닌 검사 절차형 verify는 **열거된 2종만 허용된다 [엄격]** —
     role=docs의 "drift 스캔 통과", harden의 "증거 칸 충족". 이 2종은
     오케스트레이터가 절차로 직접 수행하므로 명령 제약의 대상이 아니지만,
     목록 밖의 비-셸 verify는 실행 시 게이트 정지 대상이므로 작성하지 마라.
     목록 추가는 헌법 개정으로만 가능하다.)
   - **role 태그**: 이 태스크에 맞는 전문 역할 하나 — 예: `frontend`, `backend`,
     `db`, `test`, `infra`, `docs`. 실행 시 builder에게 해당 전문가 페르소나가
     주입된다. 애매하면 `general`.
   - **tier 태그**: `light`(보일러플레이트·설정·픽스처·단순 CRUD — 판단
     불필요) 또는 `standard`(그 외 전부). 판단이 조금이라도 들어가면
     standard. 애매하면 standard — 잘못된 light는 재시도 비용으로 절감분을
     까먹는다. 실행 시 light는 builder-light로 라우팅된다.
   - **risk 태그**: `high` 또는 `normal`(기본). 태스크의 요구사항에
     **수치·경계·개수 조건, 보안, 데이터 변형/삭제, 동시성** 중 하나라도
     포함되면 `high`. 실행 시 high 태스크는 FAIL 여부와 무관하게 처음부터
     opus 리뷰어로 라우팅된다 — 약한 리뷰어가 놓쳐서 PASS시키는 결함은
     사후 승격으로 잡히지 않기 때문이다. 태그를 생략하면 normal로 간주한다.
   를 가진다. "구현한다" 같은 모호한 태스크 금지 — verify가 안 떠오르면 태스크가 너무 크다는 뜻이니 더 쪼개라.
4. 태스크 간 의존 관계가 있으면 순서로 표현한다. **의존 순서가 최우선이다.**
   의존 관계가 동률인 태스크들 사이에서는 tier·risk가 같은 것끼리 인접하게
   정렬한다 — 모델이 바뀌면 서브에이전트 프롬프트 캐시가 갈리므로, 같은
   모델을 쓰는 태스크가 연속될수록 캐시 적중률이 높아진다.
   **서로 의존이 없고 파일이
   겹치지 않는 태스크들은 [P] 그룹으로 묶어라** — 같은 그룹은 병렬 실행된다
   (실행은 프로젝트의 `worktree:` 선언이 있을 때 워크트리 격리로, `off`면
   순차 강등 — 태그는 그대로 달아도 된다).
   그룹 표기: [P1], [P2]처럼 그룹 번호를 붙인다 (같은 번호 = 동시 실행).
   **[P] 금지 조건 2가지 [엄격]**:
   - **의존성 변경 태스크**(패키지 설치·잠금 파일 갱신)는 [P]로 묶지 않는다 —
     shared-env 워크트리에서 동일 환경에 동시 설치가 일어나면 경합한다.
   - **같은 네임스페이스를 공유하는 태스크**는 파일이 안 겹쳐도 [P]로 묶지
     않는다: 마이그레이션 버전 번호, 라우트 경로, 설정 키, 테스트 픽스처
     이름, DI 등록명처럼 **파일이 달라도 전역에서 충돌하는 것들**.
     (예: 병렬 태스크 둘이 각각 `V15__` 마이그레이션을 추가하면 파일은 안
     겹치지만 머지 시 버전이 충돌한다.) 파일 비중첩만으로는 부족하다.
5. 아키텍처 결정이 필요한 지점은 태스크로 만들지 말고 "DECISION:" 항목으로
   분리해서 맨 위에 모아라 — 이건 사용자가 결정한다 (§1 Think Before Coding).
6. **문서 태스크**: 계획에 구조 변경(새 모듈, 인터페이스 변경, 스키마 변경)이
   포함되면 해당 stage 마지막에 문서 태스크를 추가하라 (docs 스킬 기준 적용):
   `- [ ] N.x ARCHITECTURE.md 갱신 · role: docs · tier: standard · risk: normal · verify: 문서-코드 drift 스캔 통과`
   구조 변경이 없는 stage에는 넣지 않는다 — 매 stage 문서 갱신은 과잉이다.
7. **하드닝 태스크**: 프로젝트에 DB·볼륨·외부 상태가 있는데 루트에
   `HARDENING.md`가 없으면 **Stage 1에 harden 태스크를 넣는다** (harden 스킬 기준):
   `- [ ] 1.x 환경 하드닝 (L1 권한 우선) · 파일: `HARDENING.md` (신규) · role: infra · tier: standard · risk: high · verify: 점검표 각 항목의 증거 칸 충족`
   근거: 파괴 사고를 실제로 막는 층은 지시문·훅이 아니라 DB 권한이다.
   이미 HARDENING.md가 있으면 넣지 않는다 — 재점검은 트리거 발생 시에만.
8. **CLAUDE.md 수정 태스크는 stage 말미 배치 [엄격]**: CLAUDE.md(dev 루트
   헌법·프로젝트 양쪽)를 수정하는 태스크는 stage 중간에 배치하지 않는다.
   반드시 stage의 마지막 태스크로 둔다. docs·harden 스킬이 심는 태스크에도
   적용된다. 근거: 이 파일들은 모든 서브에이전트 호출의 프롬프트 캐시
   접두사에 포함되므로, 중간에 수정하면 그 stage의 남은 태스크 전부가
   캐시 미적중이 된다 (execute-plan의 "실행 중 CLAUDE.md 수정 금지" 참조).
9. **ROLES 블록**: 계획에 등장하는 role마다 2~3줄 전문가 지침을 PLAN.md의
   `## ROLES` 블록에 **1회 작성**하라 — 실행 시 오케스트레이터가 태스크
   브리핑에 이 지침을 그대로 복사해 주입한다 (태스크마다 재작성하지 않는다).
   지침은 그 role의 우선순위·가드레일 중심으로 쓴다
   (예: db → 롤백 경로 확보, test → 경계값·에러 경로 우선).

## 계약 스테이지 [엄격] — role 2종 이상 계획
role이 2종 이상인 계획은 **Stage 0을 계약 스테이지로 강제한다**:
- 산출물: 타입 정의·API 시그니처·DB 스키마 등 **트랙 간 경계가 되는 파일** +
  **계약 테스트**(mock 기반 — 각 파트가 계약을 지키는지 검증).
- 이후 모든 태스크는 다른 태스크의 **구현**이 아니라 **계약 파일**에만
  의존하도록 분해한다. 이 조건이 충족되면 [P] 그룹을 적극 부여한다 —
  계약이 경계를 고정하므로 병렬 안전성이 구조적으로 보장된다.
- 계약 스테이지 태스크는 tier=standard 고정. 대형/고위험 계획이면 grill
  심문 대상에 계약(경계 파일·계약 테스트의 충분성)을 포함한다.
- **계약 변경은 stop-the-world다**: 실행 중 계약 수정이 필요해지면
  DECISIONS급으로 승격해 전 트랙을 태스크 경계에서 멈추고 사용자 확인 후
  재개한다. builder가 계약 파일을 임의 수정하는 것은 reviewer BLOCKING
  사유다 (계약 파일은 태스크의 `.dev-kit-scope` 목록에 없으므로 Edit/Write가
  훅에서도 deny된다 — 스코프 밖 수정 = Surgical Changes 위반).
- mode S(아래) 계획은 계약 스테이지를 생략한다.

## 실행 모드 판정 (mode: S|A|B) — 계획 생성 직후
판정 결과를 PLAN.md 헤더에 1줄로 기록한다:
`mode: S|A|B (근거: 태스크 수, role 종수, 파일 겹침)`

| 모드 | 조건 | 동작 |
| --- | --- | --- |
| S | 태스크 8개 미만 또는 본질적 직렬(단일 모듈·마이그레이션) | 현행 순차. 계약 스테이지 생략 |
| A | 태스크 8개 이상 + role 2종 이상 | 계약 스테이지 + [P] 병렬 (단일 세션) |
| B | 태스크 15개 이상 + 트랙 간 파일 겹침 없음 + 트랙 분량 편차 작음 | **자동 진입 금지.** 트랙 분할안·예상 단축 폭을 출력하고 사용자 승인 대기. 승인 시 execute-plan의 mode B 런처로 진행 |

- 판정이 애매하면 **한 단계 낮은 모드**를 택한다 (S>A>B 순으로 보수적).
- 기준값(8/15)은 [유연] — 프로젝트 CLAUDE.md에서 오버라이드 가능.
- 사용자는 "B로 올려" / "순차로 해"로 언제든 오버라이드할 수 있고,
  오버라이드 사실을 PLAN.md 헤더에 기록한다
  (`mode: B (오버라이드: 사용자 지시)`).
- execute-plan은 이 헤더를 읽어 동작한다. 헤더가 없는 기존 PLAN.md는
  S로 간주한다 (하위 호환).
- mode B 후보 계획은 트랙별 **파일 소유권 목록(manifest)** 을 PLAN.md에
  기록한다 — 트랙은 자기 manifest 밖 파일을 수정할 수 없다
  (위반은 reviewer BLOCKING — 근거는 계약 스테이지의 스코프 규칙과 동일).

## 프로비저닝 [엄격] — mode 판정 직후 직접 기입
판정 결과가 요구하는 프로젝트 전제를 write-plan이 **직접 기입한다**.
사용자에게 "추가하라"고 안내하는 것을 금지한다 — 안내가 아니라 수행이
이 단계의 목적이다. 판정과 기입은 자동, 위험 판단은 보고 — 사람의 일은
보고를 읽고 결정하는 것까지만 남긴다.

- **mode A 판정 시**:
  - PLAN.md 헤더에 `mode: A (근거: …)` 기록 (위 판정 절차 — 기존 동작).
  - 프로젝트 CLAUDE.md에 `worktree:` 선언이 없으면 canonical 형식으로 추가
    (README "워크트리 격리"의 선언 형식과 동일):
    `worktree: shared-env` 또는 `worktree: isolated-env` + isolated-env일
    때만 `worktree-env-setup: <각 워크트리에서 실행할 준비 명령>`.
    값은 스택으로 판정한다 — 메인 트리 환경 재사용이 가능한 스택이면
    shared-env, 워크트리별 설치가 필요하면 isolated-env. **판정 불가면
    기입하지 않는다** (선언 없음 = off = 순차 강등 유지) — 사유를 아래
    보고 1줄에 남긴다. 위험 판단은 기입이 아니라 보고다.
  - 프로젝트 CLAUDE.md에 테스트 리소스 규칙이 없으면 추가:
    "테스트는 테스트 전용 DB/리소스만 사용한다 — 개발·공유 DB 금지."
- **mode S 판정 시**: 위 선언들을 추가하지 않는다 (불필요 권한 최소화).
  단, 이미 있으면 제거하지도 않는다.
- **mode B는 프로비저닝 대상이 아니다** — 승인 절차(위 판정 표·작성 후
  절차)를 그대로 따른다.
- 프로비저닝으로 수정 가능한 파일은 **PLAN.md·프로젝트 CLAUDE.md 2개로
  한정한다 [엄격]**. 기입 내역은 계획 출력 시 `프로비저닝: …` 1줄로
  보고한다 (기입이 없어도 `프로비저닝: 없음`으로 남긴다 — 빈칸으로
  드러나야 강제된다).

## mode 재판정 — 설계가 바뀌면 mode 기록도 따라간다
재판정 트리거는 2개:
1. **계획 수정 시**: 기존 PLAN.md를 수정(태스크 추가·삭제, stage 재구성)
   하면 mode를 재판정한다. 판정이 바뀌면 헤더를
   `mode: A (재판정: 날짜, 이전 S, 근거: …)` 형식으로 갱신하고 위
   프로비저닝을 다시 수행한다.
2. **계약 변경 stop-the-world 시**: 중단 조건 (i)로 멈춘 뒤 계획이
   수정되면 execute-plan이 재개 전에 재판정을 강제한다 (execute-plan
   중단 조건 (i) 참조).

규칙 [엄격]: 재판정으로 mode를 **올릴 때(S→A)** 는 자동 수행한다.
**내릴 때(A→S)** 는 진행 중 [P] 태스크가 없을 때만 자동이고, 있으면
현재 그룹 완료까지 기존 mode를 유지한 후 전환한다 (실행 중 스케줄링
모델이 바뀌는 것 방지). **B로의 상향은 재판정에서도 자동 진입 금지** —
승인 게이트(작성 후 절차)를 유지한다.
루프 도중의 재판정 프로비저닝이 프로젝트 CLAUDE.md를 수정하게 되면
캐시 접두사가 갈리므로, execute-plan의 "실행 중 CLAUDE.md 수정 금지"
절차에 따라 기입 후 새 세션 재개를 권고한다.

## PLAN.md 형식
```markdown
# PLAN: [기능/프로젝트명]
작성: [날짜] · 상태: IN PROGRESS
mode: A (근거: 태스크 11개, role 3종, 파일 겹침 없음)

## DECISIONS (사용자 결정 필요 — 비어있으면 생략)
- [ ] D1: [결정 사항 + 선택지 + 트레이드오프]

## ROLES (등장 role별 전문가 지침 — 브리핑에 그대로 복사됨)
- backend: 당신은 백엔드 엔지니어다. [이 프로젝트 맥락의 우선순위·가드레일 2~3줄]
- test: 당신은 테스트 엔지니어다. 경계값과 에러 경로를 우선 커버하라.

## Stage 0: 계약 — 완료 조건: 계약 테스트 green (mode A/B만 — S는 생략)
- [ ] 0.1 [경계 타입·API 시그니처·스키마 + 계약 테스트] · 파일: `contracts/...` (신규) · role: backend · tier: standard · risk: normal · verify: `npm run test -- contracts/...`

## Stage 1: [단계명] — 완료 조건: [검증 가능한 조건]
- [ ] 1.1 [기능 단위 목표 + 테스트 1~2개] · 파일: `path/to/file` · role: backend · tier: standard · risk: high · verify: `npm run test -- path/to/file.test.ts` (신규 테스트 1~2개 red→green)
- [ ] 1.2 [P1] [목표] · 파일: `...` (신규) · role: frontend · tier: standard · risk: normal · verify: `npm run test -- ...` (신규 테스트 red→green)
- [ ] 1.3 [P1] [목표] · 파일: `...` (신규) · role: test · tier: light · risk: normal · verify: [방법]

## Stage 2: ...
```

## 작성 후
- DECISIONS가 있으면 계획 실행 전에 사용자에게 결정을 요청하고 멈춰라.
- 없으면 PLAN.md 요약(단계 수, 태스크 수, 예상 리뷰 포인트)을 보여준다.
  수동 /write-plan 커맨드로 호출된 경우에만 여기서 멈추고
  "/execute-plan으로 실행 가능"을 안내한다. 자동 라우팅(헌법 §4) 경유
  시에는 DECISIONS가 없으면 헌법 §4의 **조건부 승인 게이트**를 적용한다 —
  태스크 8개 이상 또는 stage 3개 이상 / 신규 파일 5개 이상 / 스키마 변경·
  외부 API 연동·의존성 추가 포함 중 하나면 계획 출력 후 1회 확인을 기다리고,
  그 외 소형 계획은 즉시 /execute-plan 절차로 이어간다 (기준값은 [유연] —
  프로젝트 CLAUDE.md에서 오버라이드 가능).
- **mode B로 판정된 계획은 승인 게이트와 무관하게 항상 멈춘다** — 트랙
  분할안(트랙별 태스크·manifest)과 예상 단축 폭을 출력하고 사용자 승인을
  기다린다. 승인 없이 headless 트랙을 발사하지 않는다 (mode 판정 확인은
  조건부 승인 게이트와 같은 시점에 함께 제시한다 — 확인 1회로 충분하다).
  승인받으면 PLAN.md 헤더에 기록한다: `mode: B (승인: [날짜])` —
  execute-plan의 mode B 런처는 이 승인 기록이 있어야만 진입한다.
