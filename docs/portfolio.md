# 포트폴리오 — dev-kit

> `docs/journal.md`에서 출처가 `[내 판단]`·`[AI 제안→내가 채택]`인 항목만 추렸다 (`/dev-kit:journal portfolio`, 2026-10-14 생성).
> 결과 칸은 저널 근거 칸의 지표·커밋에서만 가져왔다. 지표가 없는 항목은 "측정 없음"으로 적었다.

**dev-kit** — Claude Code로 개발할 때 계획 → 구현 → 독립 검증을 자동으로 돌리는 플러그인. 구현(builder)·검증(reviewer)·상태 관리(오케스트레이터)를 서로 다른 컨텍스트로 나눠, AI가 자기 작업을 자기가 검증하는 형식화를 막는다. v1.0(2026-07) → v1.15.1(2026-10), 실프로젝트 14개에 적용.

---

1. **"업무 규칙 문제"라는 단일 진단을 받아들이지 않음** (2026-10-14)
   - 문제: AI 개발이 "계속 수정의 연속"에 빠졌고, 다른 채팅에서 "업무 규칙 문제"라는 진단을 받았다.
   - 내 결정: 단일 원인을 받아들이지 않고 증상 → 원인 → 처방으로 분해해 실측하기로 했다.
   - 결과: 원인이 규칙(S1~S3) 외에 실데이터 대조 부재(S9)·재작업 서술(S11)·브리핑 오류(S15)·화면(S4)으로 갈렸다. 이 원인들이 v1.15 처방 A~I가 됐다.

2. **규칙을 추가하기 전에 실측 진단부터** (2026-10-14) — *AI 제안 채택*
   - 문제: 대책 규칙을 기억에 의존해 바로 추가할 수 있었다.
   - 내 결정: PROGRESS FAIL 사유와 git 수정 이력에서 실패를 뽑는 읽기 전용 진단을 먼저 하고, 진단 → 설계 → 구현 단계마다 확인하기로 했다.
   - 결과: FAIL 사유 411건, 저장소 13개를 실측했다.
   - 왜 이 설계인가: 기억에 남은 실패는 최근·극적인 것에 치우친다. 기록에서 뽑아야 빈도와 현행 재현 여부를 가를 수 있다.

3. **진단에 dev-kit 실행 버전 대응을 요구** (2026-10-14)
   - 문제: 진단 1차본은 구버전 시기의 결함까지 현행 dev-kit의 결함처럼 다뤘다.
   - 내 결정: 태스크 기록 날짜를 릴리스 구간(E0~E6)에 대응시키고, 증상마다 "이미 고쳐졌는가"를 판정하게 했다.
   - 결과: 현행 v1.14 루프를 실제로 돈 프로젝트는 13개 중 4개였다. 한 프로젝트의 프롬프트 수정 11회 중 10회가 dev-kit 도입 이전이라 처방 근거에서 뺐다.

4. **기능을 넣은 것과 작동하는 것을 구분 — 병렬·화면설계 실사용 점검** (2026-10-14)
   - 문제: 병렬 실행(v1.10)과 화면 설계(v1.14)를 넣었지만 실제로 작동하는지 확인한 적이 없었다.
   - 내 결정: 다음 기능으로 넘어가기 전에 모든 프로젝트에서 `[P]` 태그 대비 실제 병렬과 화면 명세 유무를 점검했다.
   - 결과: 실제 병렬은 1개 프로젝트에서만 돌았다(그룹 내부 2.0~2.6×, 계획 전체 1.06×). v1.14 이후 시작한 2개 프로젝트의 화면 리뷰 FAIL은 0건과 1건이었다.

5. **사고 3건 — 규칙이 아니라 기계적 장치로 막는다** (2026-08-11~15)
   - 문제: 파괴 사고 2건(개발 DB 전소, 병렬 산출물 checkout 파괴)과 무손실 규칙 위반 1건(리뷰어의 Bash 수정·원복). 셋 다 마크다운 규칙이 있었는데도 일어났다.
   - 내 결정: 규칙 문구를 강화하는 대신 파괴 방어 3층(지시문 관측 → PreToolUse 훅 차단 → DB 권한), 되돌리기 범주 전면 차단, 워크트리 격리를 넣었다. 사고는 손실 여부로 등급을 나눴다.
   - 결과: 측정 없음 (v1.8.0 `ffad112`, v1.8.1 `f117f16`).

6. **사고에서 얻은 규칙이 2개월간 갇혀 있던 원인을 찾아 정식 릴리스로** (2026-10-14)
   - 문제: 회사 PC의 헌법 보강이 로컬 커밋으로만 남아 있었다. 그 분기 때문에 그 기기의 헌법이 v1.4.0에 약 2개월 고정됐다.
   - 내 결정: 로컬 커밋을 버리지 않고 원격 위로 옮겨 v1.15.1로 릴리스했다. 판단 기준도 "열거가 아니라 성질로 판단"으로 바꿨다.
   - 결과: origin main `5fc316c` (v1.15.1). 버전 불일치 원인은 reflog·부모 커밋·origin 비교로 확인했다.

7. **틀린 근거를 철회하고 결론은 검증된 근거로 유지** (2026-10-14) — *AI 제안 채택*
   - 문제: "되돌릴 수 없는 것은 ask가 아니라 deny" 원칙이 "ask가 서브에이전트에서 자동 승인될 수 있다"는 근거에 기대고 있었다.
   - 내 결정: 공식 문서로 검증하자는 제안을 채택했다. 검증해 보니 근거가 문서와 반대여서 철회했고, deny 원칙은 다른 근거(PermissionRequest 훅의 대리 응답, deny는 모든 모드에 적용)로 유지했다.
   - 결과: 측정 없음 (`5fc316c`, 문서 링크 2개).
   - 왜 이 설계인가: 결론이 맞아도 근거가 틀리면, 다음 사람이 그 근거를 반박하면서 결론까지 버린다.

8. **효과 판정 기준을 구현 전에 사전 등록** (2026-10-14)
   - 문제: v1.15가 효과가 있는지 판정할 기준이 없었다.
   - 내 결정: 첫 적용 대상(myroquant)과 판정 기준을 구현 전에 문서에 고정했다. 수치는 AI 제안(N=40, ±10%p, ×0.5/×1.5)을 채택했다.
   - 결과: 측정 없음 (판정 대기 — migrate 전후 각 40태스크).
   - 왜 이 수치인가 (AI 제안 채택분): n=40에서 10%p는 1~1.5 표준오차라 확증이 아니라 방향 판정이다. 이 한계를 기준 문서에 함께 적었다.

9. **비용 구조 — 비싼 판정은 필요한 곳에만** (2026-08-07)
   - 문제: 모든 리뷰를 상위 모델로 돌려 비용이 컸고, 태스크가 너무 잘게 쪼개져 루프 오버헤드가 컸다.
   - 내 결정: 리뷰를 하위 모델 1차 + FAIL 시 상위 모델 승격으로 2단화하고, 태스크 단위를 5~10분으로 정했다.
   - 결과: 측정 없음 (v1.5.0).

10. **결정 저널 — AI 제안과 내 판단을 구분해 기록** (2026-10-14)
    - 문제: 사용자의 입력·판단이 채팅에서 사라졌다 (질문·결정 원문 기록 13개 프로젝트 중 0개).
    - 내 결정: 모든 프로젝트를 포트폴리오로 보고, 출처 태그(`[내 판단]`/`[AI 제안→내가 채택]`/`[AI 자율]`)가 필수인 결정 저널과 과거 결정 백필을 도입했다.
    - 결과: dev-kit 저널에 백필 17항목과 2026-10-14 결정 16항목을 기록했다. 이 문서가 그 산출물이다.
