# v1.16 변경 설계 — 명세 먼저 (살아있는 명세 `docs/spec/`)

> 상태: **설계안 — 사용자 확인 대기** (2026-10-15). 구현 전이다.
> 입력:
> - 사용자 결정(2026-10-15): spec-kit의 "명세가 문서로 남고, 변경은 명세 먼저" 방식을 적용한다.
> - 근거: `docs/diagnosis-2026-10.md` §3·§7 (esi-flow), v1.15 설계 `docs/v1.15-design.md`.
> 원칙: v1.15 설계와 같다. 현행 버전에서 재현된 증상만 근거로 쓰고, 근거가 약한 항목은 보류 목록으로 보낸다.

## 0. 요지

v1.15는 규칙·화면에 **예시를 강제**했다. 하지만 그 예시가 어디에 살아 있는지는 정하지 않았다. 실측을 보면 규칙은 PLAN의 "확정 결정" 줄에 흩어지고, 화면 명세는 구현을 사후에 받아 적은 문서가 되고, DESIGN.md는 기능 하나의 스냅샷이라 프로젝트 전체 기준이 되지 못했다.

v1.16은 **프로젝트 전체 기준 명세 `docs/spec/`를 하나 두고, 모든 변경이 명세를 먼저 거치게** 한다.

| 문서 | 내용 | 수명 |
|---|---|---|
| `docs/spec/product.md` | 기능 F-n — 기능마다 인수 조건(입력·상황 → 기대 결과) | 살아있음 (프로젝트 전체) |
| `docs/spec/rules.md` | 업무 규칙 R-n — 원칙 + 예시 2개 이상(1개 경계) — v1.15 `docs/rules.md`를 옮김 | 살아있음 |
| `docs/spec/screens.md` | 화면 S-n — 액션·결과 피드백·상태 — v1.14 `docs/screens.md`를 옮김 | 살아있음 |
| `DESIGN.md` | **변경 1건의 "어떻게"** (접근법·컴포넌트·데이터 흐름·테스트 전략). "무엇"은 spec ID를 인용만 한다 | 변경 단위 스냅샷 |

기능마다 명세를 새로 쓰지 않는다. 같은 명세를 고쳐 나간다.

## 5. 적용 순서와 효과 판정

- **myroquant**: v1.15 측정 기간(v1.15 설계 §5 — migrate 후 40태스크) 동안 **v1.16을 적용하지 않는다**. v1.15 단독 효과를 교란하지 않기 위해서다.
- **esi-flow**: v1.16을 **먼저 적용**한다. 판정은 v1.15 설계 §5의 **④-b 하류 정정 / PLAN**(before 9·7건, 평균 8 → 개선 ≤ 4 · 악화 ≥ 12)과 ⑤ 같은 대상 재정의로 한다.
  - **교란 요인**: esi-flow는 아직 v1.15도 migrate하지 않았다. 그래서 esi-flow 판정은 **v1.15 + v1.16의 합산 효과**다. v1.16 단독 효과는 분리되지 않는다. 판정 보고에 이 사실을 명시한다.
- 나머지 프로젝트: v1.15 판정(myroquant)과 v1.16 판정(esi-flow)이 모두 나온 뒤에 결정한다.
