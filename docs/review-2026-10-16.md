## 2. dev-kit을 만든 의도 (대화 2) — Claude의 해석

> 리포와 맥락에서 추론한 해석이다. 출처 태그를 붙인다면 `[AI 자율]` — 사용자 확인 전이다.

- **출발점**: 코드를 한 줄씩 직접 리뷰할 수 없는 규모(프로젝트 14개)에서 AI 개발을 믿고 맡기는 장치. 신뢰를 사람이 아니라 기계적으로 확인되는 증거(독립 실행, git 커밋, 분리된 컨텍스트)에 둔다.
- **두 번째 층**: 파괴 사고(DB 전소·checkout 파괴) 이후 "지시문으로는 못 막는다"를 겪고 훅·스코프 파일·DB 권한으로 물리적 방어선을 쌓았다.
- **의도의 이동(v1.15~)**: "AI가 코드를 제대로 짜게"에서 "사람이 정해야 할 것(명세·규칙·결정)을 끌어내 고정하게"로. 결정 저널 출처 태그는 "AI가 대부분을 쓰는데 당신이 한 건 뭔가"에 증거로 답하는 장치.
- **해석**: ITSM(변경 관리·승인 게이트·감사 로그·ADR·사고 등급)의 통제 방식을 AI 개발 루프에 이식한 것. 포트폴리오 서사로는 "AI로 코딩을 잘한다"가 아니라 "AI 개발을 운영·통제할 줄 안다".

## 3. 개발 단계와 dev-kit의 현재 커버리지 (대화 3·4)

### 3-1. 사용자가 제시한 단계
> 요구사항 정의 → 데이터 설계 → 화면 설계 → 백엔드 구현 → 프론트엔드 구현 → 테스트 → 배포 → 운영

사용자 목표: **배포 전까지 자동화**. 문제의식: 요구사항·데이터 설계 문서화나 화면 설계 없이 개발만 시키니 원하는 UI·기능이 나오지 않았다. 그래서 문서화·예시 강제·화면 설계 보여주기를 요청한 것이 v1.15·v1.16으로 알고 있다. `[내 판단]`

### 3-2. 정정 (Claude)
1. 요구사항과 구현 사이에 **기술 설계(아키텍처)** 단계가 있다 — dev-kit의 DESIGN.md "어떻게".
2. **테스트는 구현 뒤 단계가 아니다** — TDD(red→green)로 구현과 섞이고, 마지막에 남는 건 통합 테스트와 **사용자 확인(인수)**.
3. **백엔드 → 프론트는 필수 순서가 아니다** — 계약(API·타입)을 먼저 정하면 병렬. dev-kit Stage 0 계약 스테이지.
4. 일직선이 아니라 **순환** — 운영 중 불편이 다음 요구사항이 된다(esi-flow 정정 9·7건 → 다음 PLAN).

## 4. "이 순서면 덜 헤맬까" (대화 5)

### 4-1. 결론
순서만으로는 부족하다. 화면 설계는 v1.14부터 순서 안에 있었지만, esi-flow는 v1.14.2 적용 **후** 완료된 결과물에서 정정 16건(9+7)이 나왔다(진단 §7-8-1). 원인은 순서가 아니라 **사용자 확인이 맨 끝에 한 번뿐**이라는 점이다.

### 4-2. 덜 헤매기 위한 세 가지
1. **확인을 앞으로 당긴다** — 데이터+화면 설계 후 클릭 가능한 목업으로 먼저 확인. 데이터 관계도 이 자리에서 같이 확인받는다("계약 1건에 건물 여러 개"는 화면을 보며 확인하기 가장 쉬운 결정).
2. **얇게 한 번 끝까지 만든다(수직 관통)** — 기능 하나를 데이터→백엔드→화면까지 가장 단순하게 관통시켜 보여준 뒤 넓힌다. 백엔드·프론트를 다 짠 뒤 처음 보여주면 데이터 구조가 틀렸을 때 전부 다시 만든다.
3. **데이터 설계에도 예시를 강제한다** — "건물 A가 계약 2건에 동시 연결 → 허용", "기간 겹치는 계약 → 허용", "빈 날짜 → 거부". ERD 그림만으로는 경계가 안 드러난다.

### 4-3. 수정된 단계
> 요구사항 → **데이터 + 화면 설계(예시 포함) → 목업으로 사용자 확인** → 기술 설계 → 계약 → **얇은 관통 구현 → 사용자 확인** → 확장 구현(테스트 포함) → 통합 테스트 → 최종 확인 → 배포 → 운영 → 다시 요구사항

### 4-4. esi-flow 정정 16건 중 데이터 관계 문제 — 1차 분류 (정정)
대화에서 Claude가 "절반 가까이"라고 했으나, 출처(`esi-flow docs/plan-contract-building.md:10-16` · `PLAN.md:9-15`, 진단 §7-8-1의 항목명)로 다시 세면 **명확 5건 + 경계 2건 / 16건**이다. 앞의 표현을 이 값으로 정정한다. 항목명만으로 분류했으므로 원문 대조가 필요하다.

## 6. 시스템 설계·장애·보안·비용 (대화 7)

사용자 질문: 현업 방식을 고려해 이 네 영역을 dev-kit에 넣을 수 있는가. `[내 판단]`

- v1.16이 비기능 요구를 "근거 행 없음"으로 보류한 것은 **측정 사각지대**다 — 진단은 PROGRESS·git만 봤고, 장애·보안·비용은 배포 후 운영에서 드러난다. 그럼에도 진단 안에 흔적: esi-flow Bearer 누락 401·PUT 전체 치환 데이터 파괴·self-lockout 재발, donmac 보안 FAIL 3, 환경·인프라 FAIL 21, S9 실환경 실패 7개 프로젝트, dev-kit 자신의 DB 전소.
- 패턴: **AI는 빠짐없이 열거·계산, 사람은 기준·한도 결정** — 규칙에 쓰던 방식(케이스 질문 → 답 → 예시 → 테스트) 그대로.
- 우선순위: 보안 > 장애(배포 전 부분) > 시스템 설계 > 비용.
- 적용 방식: 새 단계 추가가 아니라 **기존 spec 구조에 판정 필드와 예시 각도로 끼워 넣는다** (규칙 비대 방지).

## 7. 사람이 볼 문서·와이어프레임·예시 밀도 (대화 8·9·10)

### 7-1. 현재 상태
- docs 스킬 11행: "1차 독자는 에이전트, 2차가 사람". 철칙 4 "다이어그램은 텍스트 기반만". 결과: **개발·운영하면서 개발자가 볼 문서가 하나도 없다.** `[내 판단]` 사용자는 요청했다고 기억 — 데이터 설계와 같이 저널·CHANGELOG·설계 문서에 흔적 없음.
- 와이어프레임 `docs/screens/index.html`: 화면 3개 이상일 때만, 2개 이하 ASCII. 스타일 없는 로파이(의도적).
- 보기 좋은 HTML: 없음.

### 7-2. 사용자 결정 `[내 판단]`
1. **에이전트용 md를 HTML로 대체·변환하라는 뜻이 아니다.** 개발자가 볼 문서는 **추가로 필요한 별도 산출물**이다. HTML로 보기 좋게. (dev-kit 스킬 파일 수정 금지라는 뜻은 아님.)
2. **와이어프레임은 항상 만든다.** 로파이 유지.
3. **예시 확장 동의.** 단 너무 많아지면 곤란. 테스트가 느는 건 괜찮지만 **프로젝트 규모·용도에 비례**해야 한다 — 작은 것에 과도한 테스트도, 큰 것에 2개도 안 된다.
4. 분할(v1.16.1 / v1.17 / v1.18) 동의.
5. 개발자 문서 표(§7-3)의 문서·내용·독자를 그대로 기록. "목차" 이름 사용.

### 7-3. 개발자용 문서 세트 (목차) — `docs/dev/` 원본 → `docs/site/` HTML
| 문서 | 내용 | 주 독자 |
|---|---|---|
| 프로젝트 개요 | 뭘 만드는 시스템인가, 누가 쓰나, 주요 기능 목록 | 처음 합류한 개발자 |
| 시스템 구조 | 구성 요소와 연결, 기술 스택, 외부 연동, 배포 구조 | 개발자 |
| 데이터 모델 | ERD 그림 + 엔티티·관계 설명 | 개발자, DBA |
| API 명세 | 엔드포인트별 요청/응답, 예시 | 프론트·연동 개발자 |
| 화면 명세 | 화면 목록, 흐름도, 와이어프레임 링크 | 개발자, 기획 |
| 업무 규칙 | 규칙별 설명 + 예시 표 | 개발자, 현업 담당자 |
| 결정 기록 | 왜 이렇게 만들었나, 시간순 | 모두 |
| 개발 환경 | 설치, 실행, 테스트 방법 | 새 개발자 |
| 운영 가이드 | 배포 절차, 설정 항목, 장애 시 확인 순서, 백업·복구 | 운영자 |

운영 가이드가 가장 비어 있는 곳 — 현업의 운영 인수인계 문서 개념이 dev-kit에 없다.

### 7-4. 원본 방향 — "HTML 먼저 쓰고 md를 추출해야 하지 않나?" (대화 10) — **Claude 제안, 사용자 확인 대기**
사용자 질문 `[내 판단]`: 에이전트용 md에서 HTML을 추출하면 내용이 잘못될 것 같다. HTML을 먼저 쓰고 md를 추출하는 게 맞지 않나?
Claude 답: 앞 절반은 맞다 — 에이전트용 md는 압축 메모라 생성기가 설명 문장을 지어내야 하고, 그게 틀릴 수 있다. 뒤 절반(HTML 먼저)에는 반대 — HTML은 형식이지 원본이 아니다. 에이전트가 HTML을 편집하면 마크업 오류·토큰 2~3배, drift 스캔이 HTML을 대상으로 못 함, git diff 읽기 불가, HTML→md도 결국 추출.

**Claude 제안 `[AI 제안 — 미확정]`: 내용과 형식을 분리한다.** 사용자가 아직 동의하지 않았다 — 프롬프트 v1.18 Phase 2 열린 질문 Q-A1로 올렸고, 사용자의 HTML 먼저 안도 선택지로 남겼다.
```
docs/spec/*.md   에이전트용 정본 (예시 표·ID)        ← drift 스캔·테스트가 대조
docs/dev/*.md    개발자용 원본 (사람을 위한 설명문)   ← 문서 태스크가 작성, 사용자 검토. 사용자는 이 md를 보지 않는다
docs/site/*.html docs/dev/를 기계적으로 렌더링         ← 내용 변경 0
```
- 개발자 문서는 추출이 아니라 **작성**이다. 설명 문장은 사용자가 검토한다.
- HTML은 렌더링만 — 잘못될 지점이 없다.
- 두 원본이 공유하는 사실(예시 표·엔티티·화면 목록)은 `{{spec:R3}}`처럼 **ID 참조로 렌더링 시점에 끼워 넣는다** (transclusion). 손으로 옮겨 적지 않으니 어긋날 수 없다 — docs 스킬 "손으로 옮겨 적는 명세는 drift 1순위" 원칙과 같은 논리.
- 남는 오류 경로 2개는 기존 장치로 잡힌다: 설명문 오류 → 사용자 검토, 사실 오류 → spec drift 스캔.

### 7-9. 비용 범위 확정 (대화 12, 10-17)
사용자 `[내 판단]`: 비용 최적화는 둘 다 — 상용화(배포)까지 **루프 토큰 비용**을 아끼고, 운영·유지보수 관점에서도 비용이 최적화되고 **합리적인 가격**이어야 한다.
- 새로 드러난 전제: dev-kit으로 만드는 프로젝트 중 **상용화 대상**이 있다. scale=product의 정의가 "외부 사용자·돈·개인정보"에서 "**판매·과금되는 제품**"으로 명확해진다.
- 루프 비용 배치 (Claude 제안 `[AI 제안]` 미확정): 측정 장치는 v1.16.1에 먼저(루프 동작을 바꾸지 않아 v1.15·v1.16 측정 교란 없음), 절감 조치는 판정 뒤 v1.19(P4 통폐합과 합침). 근거: 루프 고정비용 바닥 13m(tier=light 중앙값)·승인 대기·기록 절차를 다음 표적으로 삼은 기존 결정.
- 제품 비용은 v1.18 (C)에 — scale=product면 **운영 비용 추정 표**(인프라·유료 API·저장 가정 → 사용자당 월 비용)를 DESIGN.md 비기능 요구에 포함. 값은 사용자가 주고, 모델이 채우지 않는다.
