# Debugging — 조사 없이 수정 없다

분류: **[엄격]** — 4단계를 정확히 따른다. 급하다는 맥락은 완화 사유가 아니다.

| 변명 | 현실 |
|---|---|
| 급하니까 일단 고치자 | 조사 없는 수정은 새 버그를 만들고 더 느리다 |
| 증상이 사라졌으니 됐다 | 증상 제거 ≠ 원인 제거 |
| 명백한 원인이다 | 명백해 보이는 원인의 절반은 공범일 뿐이다 |

## 4단계

### 1. 재현
최소 재현 케이스를 만든다. **재현 못 하면 수정도 없다** — 재현이 안 되면
재현 조건을 좁히는 것이 이번 작업의 전부다.

### 2. 격리
변수를 하나씩 제거해 범위를 축소한다. 관련 코드는 **완전히 읽는다** —
일부만 읽고 세운 가설은 조사가 아니라 추측이다.

### 3. 역추적
증상 지점에서 호출 사슬을 거꾸로 타고 최초 트리거를 찾는다.
**증상을 보는 것 ≠ 원인을 이해한 것.** "여기서 값이 이상하다"에서 멈추지
말고 "왜 이 값이 여기까지 도달했나"까지 간다.

### 4. 수정 + 다층 방어
- 수정 전에 **실패하는 재현 테스트를 먼저** 만든다 (헌법 §3 TDD와 연결 —
  red를 실제로 확인).
- 근본 원인을 수정한다.
- 원인 경로의 다른 층에도 검증을 추가한다 — 같은 계열 버그의 재발 방어.

## 종료 조건
- 재현 테스트 green + **원인을 한 문장으로 설명 가능**. 둘 중 하나라도
  안 되면 끝난 게 아니다.
- 3회 수정 실패 시 멈추고, 조사 내용(재현 조건, 배제한 가설, 남은 용의자)과
  함께 보고한다.
