# Brainstorming — 아이디어를 설계로

분류: **[유연]** — 질문 방식·순서·접근법 수는 맥락에 맞게 적응한다.
단 "최소 안전선"(목적·성공 기준·비범위 3개 확보 후 진행 — UI가 있는
프로젝트면 **화면 목록 확정** 포함)은 **[엄격]**.

목적: 모호한 아이디어를 대화로 좁혀 **DESIGN.md**(승인된 설계 문서)를 만들고,
/write-plan 절차로 넘긴다. 이 스킬이 활성인 동안 **구현 금지, PLAN.md 생성 금지.**

## 절차

### 1. 컨텍스트 파악 (질문 전에)
프로젝트의 기존 파일·문서·최근 커밋을 먼저 훑는다. 빈 프로젝트면
사용자의 다른 프로젝트 관례(스택, 구조)를 물어볼 준비를 한다.

### 2. 질문으로 좁히기
- **한 번에 질문 하나.** 여러 개를 쏟아내지 않는다.
- **객관식 우선.** 열린 질문보다 "A/B/C 중 어느 쪽?"이 답하기 쉽다.
  열린 질문은 객관식으로 못 만들 때만.
- 커버할 것: **목적**(누가 왜 쓰나) → **핵심 시나리오**(가장 중요한 사용 흐름
  1~3개) → **제약**(스택, 기존 시스템 연동, 예산/기간) → **성공 기준**
  (뭐가 되면 완성인가) → **비범위**(안 만들 것 — 명시적으로).
- 답이 이미 대화/컨텍스트에 있으면 묻지 말고 확인만 한다.

### 3. 접근법 제시
이해가 됐다고 판단되면 **2~3개 접근법을 트레이드오프와 함께** 제시하고,
추천안을 이유와 함께 앞세운다. 사용자가 고르면 진행.

### 4. 설계 섹션별 확인
설계를 한 번에 다 쓰지 말고 섹션 단위로 제시하고 각각 확인받는다:
사용자/화면/플로우(UI가 있으면 — 아래 화면 설계) → 아키텍처 → 컴포넌트 →
데이터 흐름 → 에러 처리 → 테스트 전략.
단순한 섹션은 몇 문장, 복잡한 섹션은 200~300단어까지. 확인 중 어긋나면
앞 단계로 돌아가는 것을 주저하지 않는다.

#### 화면 설계 (UI가 있는 기능 한정)
기능 설계만으로 실행하면 화면·플로우가 builder 즉흥으로 정해지고, 검증
사슬이 verify 명령 기반이라 "쓰기 불편함"은 어느 층에서도 안 잡힌다 —
화면 스펙을 상류(설계)에서 확정해 verify·추적표·drift 검사에 관측 가능하게
걸리도록 한다.

- **화면 목록**: 에이전트가 DESIGN.md 핵심 시나리오에서 화면 목록 초안을
  뽑아 객관식으로 확인한다 (한 번에 질문 하나 — 기존 원칙 동일).
- **화면당 확정 항목**: 목적 · 진입 경로 · 주요 액션 1~2개와 각 액션의
  결과 피드백(이동/토스트/인라인 갱신) · 입력 필드(있으면 필수 여부·검증
  실패 문구) · 상태 3종(빈/로딩/에러) · 뒤로 가기·이탈 시 동작 · 완료 후 이동.
- **저장 전 시나리오 걷기 [엄격]**: 핵심 시나리오(DESIGN.md의 1~3개)를
  각각 정상 경로 + 실패 경로 1개씩 화면 순서대로 걸어본다 —
  "시나리오 A: 화면1 → 액션 → 화면3 → ..." 형태로 제시하고 사용자 확인.
  완주가 안 되면 화면 추가 또는 흐름 수정 후 저장한다. 어느 핵심 시나리오도
  지나지 않는 화면은 보조 시나리오로 한 줄 흐름만 적거나(걸어보지 않음)
  불필요하면 제거한다 — 어느 쪽인지 사용자에게 확인한다. 핵심 시나리오가
  5개를 넘으면 설계 분해 대상이다(기존 서브프로젝트 분해 규칙).
- **저장**: 확정본을 `docs/screens.md`로. 템플릿: 화면 목록 → 화면당 위
  확정 항목 + ASCII 배치 → 핵심 시나리오 흐름 → 보조 시나리오 흐름.
- **로파이 목업**: 화면 3개 이상이면 `docs/screens/index.html` 로파이
  목업을 같이 만든다 (스타일 없는 박스·텍스트·버튼, 화면 간 링크로 플로우
  확인용). 2개 이하면 ASCII만 [유연]. 목업 생성은 tier=light 성격의 기계적
  작업이다 — 오케스트레이터가 직접 짜지 않고 builder-light에 위임한다.
- 사용자가 목업을 보고 수정을 말하면 screens.md를 고치고, HTML은 확정 후
  1회만 재생성한다.

### 5. DESIGN.md 작성
승인된 내용을 프로젝트 루트 DESIGN.md로 저장:

```markdown
# DESIGN: [이름]
## 목적 / 사용자
## 범위 / 비범위
## 접근법 (선택 이유 + 기각된 대안)
## 사용자 / 화면 / 플로우 (UI가 있으면 — docs/screens.md 참조)
## 아키텍처 / 컴포넌트
## 데이터 흐름
## 에러 처리
## 테스트 전략
## 미해결 (있다면 — write-plan의 DECISIONS 후보)
```

저장 전 자기 점검: 플레이스홀더·상호 모순·비범위 침범이 없는지 확인하고 고친다.

### 6. 핸드오프
DESIGN.md 승인 후 **/write-plan 절차로 이어간다** (DESIGN.md를 입력으로
PLAN.md 생성). 대형/고위험 설계면 write-plan 전에 grill 스킬로 심문을 제안한다.

## 원칙
- **YAGNI 무자비하게** — 모든 접근법에서 불필요 기능을 걷어낸다.
- 프로젝트가 한 설계로 감당 안 되게 크면 서브프로젝트로 분해를 돕고,
  첫 서브프로젝트부터 이 절차를 다시 돈다.
- 사용자가 "그냥 만들어"라고 재촉해도, 목적·성공 기준·비범위 3개는
  확보한 후에 넘어간다 (최소 안전선).
