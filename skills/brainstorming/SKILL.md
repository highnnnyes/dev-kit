# Brainstorming — 아이디어를 설계로

분류: **[유연]** — 질문 방식·순서·접근법 수는 맥락에 맞게 적응한다.
단 "최소 안전선"(목적·성공 기준·비범위 3개 확보 후 진행 — 화면 설계
대상(ui: interactive·static — 4단계의 대상 판정)이면 **화면 목록 확정**
포함, 규칙 대상(rules: — 4단계)이면 **규칙마다 예시 2개 이상** 포함)과
질문 커버리지 표·결정 저널 기록은 **[엄격]**.

목적: 모호한 아이디어를 대화로 좁혀 **살아있는 명세 `docs/spec/`**(프로젝트 전체
기준 — product.md 기능 F#, rules.md 규칙 R#, screens.md 화면 S#)를 만들거나
고치고, 이번 변경의 "어떻게"를 담은 **DESIGN.md**를 만든 뒤 /write-plan 절차로
넘긴다 (v1.16). 명세는 기능마다 새로 쓰지 않는다 — 이미 있으면 **수정안(diff)**을
만들어 확인받는다. 이 스킬이 활성인 동안 **구현 금지, PLAN.md 생성 금지.**

## 절차

### 1. 컨텍스트 파악 (질문 전에)
프로젝트의 기존 파일·문서·최근 커밋을 먼저 훑는다. 빈 프로젝트면
사용자의 다른 프로젝트 관례(스택, 구조)를 물어볼 준비를 한다.

### 2. 질문으로 좁히기
- **한 번에 질문 하나.** 여러 개를 쏟아내지 않는다.
- **객관식 우선.** 열린 질문보다 "A/B/C 중 어느 쪽?"이 답하기 쉽다.
  열린 질문은 객관식으로 못 만들 때만.
- 커버할 것: **목적**(누가 왜 쓰나) → **핵심 시나리오**(가장 중요한 사용 흐름
  1~3개) → **제약**(스택, 기존 시스템 연동, 예산/기간) → **성공 기준**
  (뭐가 되면 완성인가) → **비범위**(안 만들 것 — 명시적으로).
- 답이 이미 대화/컨텍스트에 있으면 묻지 말고 확인만 한다.
- 위 5항목은 **최소 안전선**일 뿐이다 — 추상 단위라 큰 질문 몇 개로 끝나기
  쉽다. 5항목 확보 후 **케이스 단위 질문**으로 내려간다: 규칙·화면마다
  "입력 X면 결과는?" 형태 (예: "건물 A가 연결그룹에 속하면 보고서는 몇
  부?", "같은 1분봉에 지정가와 손절이 함께 닿으면 어느 쪽이 먼저?").
  경계·예외 입력(0·빈 값·정확히 경계값·동시 발생·정지/휴장)을 우선한다.
  같은 규칙의 케이스 3~5개는 **표 한 장으로 묶어** 물어도 된다 —
  "한 번에 질문 하나"의 유일한 예외다 (케이스 질문이 많아 왕복이 과도해지는
  것을 막는다) [유연].
  근거: 실측 진단(dev-kit 리포 docs/diagnosis-2026-10.md §1-4) — 결정 기록이 남은
  6개 프로젝트 모두 케이스 단위 질문 0건이었고, 경계 규칙은 전부 구현 중
  FAIL 후에야 사용자에게 물었다.
- **질문 커버리지 표 [엄격]**: 질문하면서 DESIGN.md `## 질문 커버리지`
  표를 채운다 — 영역(목적·시나리오·제약·성공 기준·비범위 + 규칙 R# +
  화면)마다 `추상 질문 수 / 케이스 질문 수 / 미결`. 케이스 질문이 0인
  영역은 0으로 적는다(빈칸 금지 — 0이 드러나야 강제된다). 미결은
  write-plan의 DECISIONS 후보다.

### 3. 접근법 제시
이해가 됐다고 판단되면 **2~3개 접근법을 트레이드오프와 함께** 제시하고,
추천안을 이유와 함께 앞세운다. 사용자가 고르면 진행.
사용자가 고르면 `docs/journal.md`에 항목을 남긴다 — 선택지·기각안·이유와
출처 태그(AI가 제시한 안 중에서 골랐으면 추천 여부와 무관하게
`[AI 제안→내가 채택]`, 사용자가 제시안에 없던 새 안을 냈을 때만
`[내 판단]`). 형식은 docs 스킬 "결정 저널" [엄격].

### 4. 설계 섹션별 확인
설계를 한 번에 다 쓰지 말고 섹션 단위로 제시하고 각각 확인받는다:
사용자/화면/플로우(UI가 있으면 — 아래 화면 설계) → 아키텍처 → 컴포넌트 →
데이터 흐름 → 에러 처리 → 테스트 전략.
단순한 섹션은 몇 문장, 복잡한 섹션은 200~300단어까지. 확인 중 어긋나면
앞 단계로 돌아가는 것을 주저하지 않는다.

#### 명세 원칙 [엄격] (v1.16)
- **"기준: 현재 구현"·"코드가 정본" 형태의 명세 작성 금지** — 명세는 의도된
  동작을 적는다. 구현과 다르면 그것이 drift이고, 어느 쪽을 고칠지는 사용자가
  정한다. 근거: 구현을 사후에 받아 적은 화면 명세로는 흐름 결정이 고정되지
  않았다 (dev-kit 리포 docs/diagnosis-2026-10.md §7-1-3 · §7-3 S4).
- ID는 하이픈 없이 `F3`/`R3`/`S3`, 예시는 `F3-예1`. **ID는 재사용하지 않는다** —
  폐기한 항목은 `(폐기 YYYY-MM-DD, 대체: R9)`로 남긴다 (반복 계수 키라서).
- 기존 `docs/spec/`이 있으면 새로 쓰지 않고 **diff로 제시**해 확인받는다 —
  바뀌는 항목 ID와 예시 행만 보여준다.

#### 기능 정의 — `docs/spec/product.md` [엄격] (v1.16)
기능마다 `### F3. [기능명]` + 목적 1줄 + **인수 조건 표**
(`| 예시 | 입력·상황 | 기대 결과 |`, 2개 이상, 1개 이상은 실패·경계). 예시 칸이
비면 저장 금지 (rules.md와 같은 규칙). 예시 ID는 write-plan에서 테스트 케이스
ID가 된다.

#### 업무 규칙 정의 (rules: 대상 한정) [엄격]
**대상 판정**: 설계에 계산·판정·분류·수치 기준·상태 전이 규칙이 하나라도
있으면 대상이다 (세금 계산, 체결 순서, 종목 선정, 라벨 분류, 휴장 판정 등).
대상이 아니면 DESIGN.md에 `rules: none (근거 1줄)`을 남긴다. 판정이 애매하면
사용자에게 객관식으로 묻는다 — **모델이 스스로 none으로 좁히지 않는다**
(ui: 판정과 동일 규칙).

대상이면 화면 설계 **전에** `docs/spec/rules.md`를 확정한다:
- **용어집**: 도메인 용어 → 정의 1줄 (같은 말을 다르게 쓰는 것을 막는다).
- **규칙 R1, R2, …**: 규칙마다 원칙 1줄 + **입력 → 기대 결과 예시 2개
  이상**. 예시 중 **1개 이상은 경계·예외 케이스**다.
  ```markdown
  ### R3. 같은 봉 체결 순서
  원칙: 같은 봉에서 여러 주문이 닿으면 시가에 가까운 가격부터 처리한다.
  | 예시 | 입력 | 기대 결과 |
  |---|---|---|
  | R3-예1 | 시가 100, 지정가 매수 98, 손절 95 | 98 체결 → 95 손절 |
  | R3-예2 (경계) | 지정가 = 손절 = 97 | 진입 먼저, 손절은 다음 봉부터 |
  ```
- **예시 칸이 비면 저장 금지 [엄격]** — 예시 없는 규칙은 해석이 builder
  즉흥이 되고, 테스트가 구현에서 도출된다. 실측: 사후에 드러난 규칙
  결함은 전부 예시가 없던 경계 케이스였다 (진단 S1·S3).
- 예시 ID(`R3-예1`)는 write-plan에서 테스트 케이스 ID가 된다 — 예시 행이
  곧 테스트다.
- 확정 후 journal.md에 항목을 남긴다 (규칙별 결정 출처 태그 포함).

#### 화면 설계 대상 판정 [엄격]
"UI가 있는 설계"란 **사람이 보는 화면 산출물이 있는 설계**다. 웹 UI·
프론트엔드 프레임워크 유무가 기준이 아니라 **산출물**이 기준이다 —
HTML 리포트도 대상이다. 세 유형 중 하나로 판정해 DESIGN.md에 기록한다
(write-plan이 이 값을 PLAN.md 헤더 `ui:` 필드로 옮긴다):
- **interactive**: 사용자가 조작하는 화면(입력·클릭·이동). 아래 화면 설계
  절차 전부 적용.
- **static**: 조작 없는 산출물 — 리포트·대시보드 스냅샷·이메일·PDF.
  아래 절차를 다음과 같이 축약 적용한다:
  - screens.md의 "화면" = 페이지/섹션. 화면당 확정 항목은 목적·진입
    경로(누가 언제 받아 보나)·상태 3종만 — 주요 액션·입력 필드·뒤로
    가기·완료 후 이동은 생략.
  - 상태 3종은 빈/로딩/에러 대신 **데이터 없음 / 부분 데이터 / 생성 실패**.
  - 시나리오 걷기는 **"독자가 이 리포트에서 답을 찾는 순서" 1개**만.
  - 휴리스틱은 **현재 위치·일관성·에러 문구 3개만** 적용 (실행 취소·
    기억·입력 부담은 조작이 없으므로 해당 없음).
  - 저장·로파이 목업 규칙은 동일(3페이지 이상이면 builder-light 위임).
- **none**: 화면 산출물 없음 — CLI·라이브러리·배치·API 전용. 화면 설계
  대상 아님. DESIGN.md에 근거 1줄을 남긴다.

판정이 애매하면 **사용자에게 객관식으로 묻는다**. 모델이 스스로 none으로
좁히지 않는다 [엄격] — "웹 UI 없음 = 화면 없음"으로 판단해 HTML 리포트
프로젝트가 screens.md 없이 write-plan으로 넘어간 실측 오판이 이 규칙의
근거다.

#### 화면 설계 (ui: interactive·static 한정 — static은 위 축약 규칙)
기능 설계만으로 실행하면 화면·플로우가 builder 즉흥으로 정해지고, 검증
사슬이 verify 명령 기반이라 "쓰기 불편함"은 어느 층에서도 안 잡힌다 —
화면 스펙을 상류(설계)에서 확정해 verify·추적표·drift 검사에 관측 가능하게
걸리도록 한다.

- **화면 목록**: 에이전트가 DESIGN.md 핵심 시나리오에서 화면 목록 초안을
  뽑아 객관식으로 확인한다 (한 번에 질문 하나 — 기존 원칙 동일).
- **화면당 확정 항목**: 목적 · 진입 경로 · 주요 액션 1~2개와 각 액션의
  결과 피드백(이동/토스트/인라인 갱신) · 입력 필드(있으면 필수 여부·검증
  실패 문구) · 상태 3종(빈/로딩/에러) · 뒤로 가기·이탈 시 동작 · 완료 후 이동.
- **저장 전 시나리오 걷기 [엄격]**: 핵심 시나리오(DESIGN.md의 1~3개)를
  각각 정상 경로 + 실패 경로 1개씩 화면 순서대로 걸어본다 —
  "시나리오 A: 화면1 → 액션 → 화면3 → ..." 형태로 제시하고 사용자 확인.
  완주가 안 되면 화면 추가 또는 흐름 수정 후 저장한다. 어느 핵심 시나리오도
  지나지 않는 화면은 보조 시나리오로 한 줄 흐름만 적거나(걸어보지 않음)
  불필요하면 제거한다 — 어느 쪽인지 사용자에게 확인한다. 핵심 시나리오가
  5개를 넘으면 설계 분해 대상이다(기존 서브프로젝트 분해 규칙).
- **저장 전 휴리스틱 점검 [엄격]**: 시나리오 걷기 직후, 닐슨 10원칙을
  화면 설계용으로 줄인 아래 5개를 체크리스트로 확인한다. 각 질문은
  docs/spec/screens.md만 보고 답할 수 있어야 하고, 답이 "적혀 있지 않음"이면
  그것이 지적이다. 걸리는 항목은 저장 전에 screens.md에 반영하거나
  사용자에게 확인한다 (이 점검으로 screens.md가 바뀌어도 HTML 목업
  재생성은 기존 규칙대로 확정 후 1회):
  - 현재 위치: 어느 화면·어느 단계인지 화면 자체에서 보이는가
    (제목·단계 표시·활성 탭)
  - 실행 취소: 되돌릴 수 없는 액션(삭제·결제·발송) 앞에 확인이 있고,
    되돌릴 수 있는 액션은 확인 없이 바로 되는가. 뒤바뀐 곳은 없는가
  - 일관성: 같은 종류의 액션(저장·취소·뒤로)이 화면마다 같은 위치·
    같은 이름인가
  - 에러 문구: 에러 상태가 "무엇이 잘못됐고 다음에 뭘 하면 되는지"를
    말하는가, "오류가 발생했습니다"인가
  - 기억·입력 부담: 앞 화면 값을 외워서 다음 화면에 입력하거나,
    시스템이 이미 아는 값(날짜·기본값·이전 선택)을 다시 묻는 곳이 있는가
- **저장**: 확정본을 `docs/spec/screens.md`로 (화면마다 `### S3. 화면명` — ID는
  재사용하지 않는다). 템플릿: 화면 목록 → 화면당 위
  확정 항목 + ASCII 배치 → 핵심 시나리오 흐름 → 보조 시나리오 흐름.
- **로파이 목업**: 화면 3개 이상이면 `docs/screens/index.html` 로파이
  목업을 같이 만든다 (스타일 없는 박스·텍스트·버튼, 화면 간 링크로 플로우
  확인용). 2개 이하면 ASCII만 [유연]. 목업 생성은 tier=light 성격의 기계적
  작업이다 — 오케스트레이터가 직접 짜지 않고 builder-light에 위임한다.
- 사용자가 목업을 보고 수정을 말하면 screens.md를 고치고, HTML은 확정 후
  1회만 재생성한다.
- screens.md 확정 후 journal.md에 항목을 남긴다.

#### 디자인 확인 (ui: interactive·static 한정) [엄격]
screens.md는 동작·상태의 스펙이고 시각 디자인이 아니다. 시각 디자인 불만은
PROGRESS에 기록되지 않는 유형이라 루프가 잡지 못한다 — 구현 전에 디자인
자료를 확정해 화면 기준으로 삼는다. 근거: esi-flow UI 전면 재설계 결정
(2026-09-30, 사용자 결정 — dev-kit 리포 docs/v1.15-design.md §1 C).

1. **경로 판정**: 이 세션에 Artifact 도구가 있고 Design 타입을 쓸 수 있으면
   (quickstart intent=design으로 확인) 경로 ①, 아니면 경로 ②.
   - **경로 ①**: screens.md의 화면당 아트보드 1개로 디자인 캔버스를 만든다
     (디자인 시스템은 사용자에게 고르게 한다). 사용자가 검토·수정한 확정본을
     Artifact read로 받아 `docs/design/`에 저장한다 (화면당 HTML 또는 이미지).
   - **경로 ②**: **"디자인 순서입니다"라고 멈춘다.** 받을 자료를 지정해
     요청한다 — Claude Design의 Share → Handoff to Claude Code(ZIP) 또는
     HTML/PDF export, 또는 사용자가 `/design`으로 만든 캔버스. 저장 위치
     `docs/design/`, 화면명은 screens.md와 같게. 자료가 들어오기 전에는
     다음 단계로 가지 않는다.
2. **대조 [엄격]**: 자료가 들어오면 screens.md와 **화면별로 대조**해 차이
   목록을 만든다 — 화면·요소·액션·상태 단위로 "스펙에만 있음 / 디자인에만
   있음". 대조는 HTML·스크린샷만 전제한다 (Handoff 번들 내부 형식은 공식
   문서 미확인 — 부가 파일은 참고만).
3. **해소**: 차이마다 screens.md 수정 또는 디자인 수정 중 하나를 사용자가
   정한다. 차이가 0이 되기 전에는 write-plan으로 넘어가지 않는다.
4. 결과를 DESIGN.md에 `design: docs/design/ (대조 완료 날짜)`로 기록한다.
   사용자가 디자인 단계를 생략하겠다고 하면 `design: skip (사유)`로 남긴다
   — 모델이 스스로 skip을 고르지 않는다. 확정·생략 모두 journal.md 항목.

### 5. DESIGN.md 작성
승인된 내용을 프로젝트 루트 DESIGN.md로 저장:

```markdown
# DESIGN: [이름]
## 목적 / 사용자
## 범위 / 비범위
## 접근법 (선택 이유 + 기각된 대안)
## 인용 spec ID — 이번 변경이 다루는 F#·R#·S# 목록
## spec diff 요약 — 이번에 추가·변경·폐기한 항목 (docs/spec/ 커밋 참조)
## 업무 규칙 — rules: docs/spec/rules.md | none (none이면 근거 1줄 — 규칙 내용은 쓰지 않고 R# 인용)
## 사용자 / 화면 / 플로우 — ui: interactive | static | none (none이면 근거 1줄, 화면 내용은 쓰지 않고 S# 인용)
## 디자인 — design: docs/design/ (대조 완료 날짜) | skip (사유) | n/a (ui: none)
## 아키텍처 / 컴포넌트
## 데이터 흐름
## 에러 처리
## 테스트 전략
## 미해결 (있다면 — write-plan의 DECISIONS 후보)
## 질문 커버리지 (영역 | 추상 질문 수 | 케이스 질문 수 | 미결 — 빈칸 금지)
```

저장 전 자기 점검: 플레이스홀더·상호 모순·비범위 침범이 없는지 확인하고 고친다.

### 6. 핸드오프
DESIGN.md 승인을 journal.md에 기록한 뒤 **/write-plan 절차로 이어간다** (DESIGN.md를 입력으로
PLAN.md 생성). 대형/고위험 설계면 write-plan 전에 grill 스킬로 심문을 제안한다.

## 원칙
- **YAGNI 무자비하게** — 모든 접근법에서 불필요 기능을 걷어낸다.
- 프로젝트가 한 설계로 감당 안 되게 크면 서브프로젝트로 분해를 돕고,
  첫 서브프로젝트부터 이 절차를 다시 돈다.
- 사용자가 "그냥 만들어"라고 재촉해도, 목적·성공 기준·비범위 3개는
  확보한 후에 넘어간다 (최소 안전선).
